## Local walk (before any paid window)

The fake CLI checks what the kits send to Colab; it does not run the remote script. A local walk does: it runs the lane 3 remote script end to end on a Linux box, with real uv, the real interpreter download, the real lock, the real local wheels and the real ai-toolkit pin. It costs nothing and found three defects that the fake suite had passed (window `sdlab-l3-stub-4`'s lock file, a missing `torchaudio`, and a training failure with no `REFUSED` line).

1. **Emit the script.** `bash scripts/colab/launch_lane3_stub.sh --emit-remote-script <dir>/remote_lane3_stub.sh` writes the script through the same function the live path uploads with (`scripts/colab/launch_lane3_stub.sh:48`), so the file is byte for byte what a window would run, and writes `<dir>/remote_lane3_stub.sh.env` with the `KEY=VALUE` lines the kit passes to `colab exec --env` (`:469-490`). It exits before the pre-flight and makes no `colab` call. With any window option (`--out-dir`, `--session`, `--card`, `--wheel-dir`, `--cap`, `--wall-s`, `--grace-s`, `--margin`) it is refused `EMIT_REMOTE_SCRIPT_EXCLUSIVE` (`:573-594`; `tests/colab/test_lane3_local_wheels_lock.py`).
2. **Stage `/content` as the uploads leave it**, flat: `lane3.lock`, `lane3-local-wheels.json`, both wheels, `launch_guards.py`, `classify_install_log.py` and the emitted script.

**What the lane 3 CPU stub proves now (from the install-path change):** the pinned uv, the CPython 3.12.15 build `20261021`, the hash-locked `lane3.lock`, the two local wheels, the ai-toolkit pin and the import gate, on the VM, ending with `TRAIN_SKIPPED`, `train: skipped_cpu_stub` and a downloaded bundle of the install evidence. **Why lane 3 training cannot run on a CPU VM (walk of 2026-11-06):** ai-toolkit at `beb94824` imports every built-in extension when it builds a job, and `extensions_built_in/diffusion_models/omnigen2/src/ops/triton/layer_norm.py:46` calls `torch.cuda.current_device()` at import time, so on any machine without an NVIDIA driver (a Colab CPU VM included) `run.py` fails with `RuntimeError: Found no NVIDIA driver on your system`. ## Lane 3 GPU rung

**The guards (train mode, on the VM, before any model download)** — `lane3_rung.py guards`, each a `REFUSED: <CODE>` line on the exec stream and in `setup.log`, carried into `window.json` as `refusal_code`, with every measurement in `window.json` under `train_guards` whether it passes or not:
- `GPU_SMOKE_FAILED`: a bf16 1024x1024 matmul loop on cuda for about 5 s through the lane's own torch, then one bitsandbytes `AdamW8bit` step on a 1024x1024 bf16 Parameter. Recorded: device name, driver (`nvidia-smi`), `torch.version.cuda`, torch and bitsandbytes versions, iterations, seconds, TFLOPS. Colab's A100 driver is 580.82.07 (CUDA 13.0) per the studio's rdlab receipts; plain torch matmul ran on it, the bitsandbytes CUDA binary had not.
- `DISK_FREE_LOW`: free bytes on every distinct filesystem holding `/content/hf_home` or `/content/lane3_train` must be at least 75 GiB.
- `HOST_RAM_LOW`: `MemAvailable` must reach `LANE3_HOST_RAM_REQUIRED_GIB`, which the request sets from walk (a)'s measured peak host RSS + 20% (`HOST_RAM_THRESHOLD_MISSING` without it; no default). `MemTotal` is recorded too.
- `/dev/shm` size is recorded (no threshold); the rung YAML sets `num_workers: 0`, so no forked dataloader worker uses it.

**The download** — `lane3_rung.py download` fetches the model at `LANE3_MODEL_REVISION` into `/content/hf_home` with the request's read token. The kit takes the token only from `HF_TOKEN_GGUF_READ` in the rig's environment (`HF_READ_TOKEN_MISSING` without it), before any `colab` call writes it to a mode-600 file in a private tmpfs directory (`HF_TOKEN_STAGING_FAILED` otherwise) (`$XDG_RUNTIME_DIR` or `/dev/shm`; removed by the EXIT trap) and uploads that file to `/content/lane3_hf_read_token` (`scripts/colab/launch_lane3_stub.sh:886-900`, `:943-946`). It never goes in `--env` or any argv: google-colab-cli 0.7.4 turns `--env` into `os.environ[...]` lines prepended to the cell code (`colab_cli/commands/execution.py:65-71`, `:235`) and logs that code to `~/.config/colab-cli/history/<session>.jsonl` (`:265`), and argv is visible in `ps`. The VM reads the file into a shell variable and shreds it (`shred -u`, unlink as fallback; `HF_TOKEN_SHRED_FAILED` if it survives) before anything else runs (`:55-70`), and passes it to the download step's environment only. Only `hf_token_used` is recorded; every log is scrubbed of `hf_` tokens, and so is every line the VM streams back (`remote_runner.py`, `lane3_bundle_now.py`), because exec outputs go into the CLI history too; the kit prints a reminder to check the CLI history after the window (`:838`) and never reads it. Before any spend the kit checks the model at the pinned revision with the same token from the rig (`lane3_rung.py model-check`, stdlib, token in a header, and a redirect to another host is refused so the header never follows it; `:874-884`), and the VM names a failed metadata call the same way: `MODEL_AUTH_FAILED` (401/403), `MODEL_REVISION_NOT_FOUND`, `MODEL_METADATA_FAILED` (`lane3_rung.py:318-378`). After the first 60 s or 2 GiB of new bytes the time for the remaining bytes is projected from the measured rate; a projection over `LANE3_DOWNLOAD_MAX_SECONDS` stops with `DOWNLOAD_TOO_SLOW` (`DOWNLOAD_LIMIT_MISSING` without it), and a thread kills the download at that limit whatever the probe said (`:470`, `:507`), so a stall that still prints progress cannot run on to the wall. Recorded: bytes, seconds, MB/s, the probe, the hard-limit flag, lines with `429` and with retries. The rig's own unauthenticated download of Qwen/Qwen-Image at `75e0b4be` (2026-11-06) took 834 s for 57.70 GB (about 69 MB/s) with no 429.

**The rung shape** — `--train` requires `--rung-job 20|500` (`RUNG_JOB_REQUIRED`; no default; `--rung-job` without `--train` is `TRAIN_OPTION_WITHOUT_TRAIN`), recorded in `window.json` as `rung_job` and `rung_job_sha256`. `scripts/colab/lane3/rung-qwen-image.yaml` (`--rung-job 20`) and `scripts/colab/lane3/rung-qwen-image-500.yaml` (`--rung-job 500`) are the rustline v5 config (`rustline_v5_ckpts/config.yaml`, sha256 `44bf1604...f677f`): the 20-step job sets `steps`, `save_every` and `sample_every` at 20, and the 500-step job sets `steps: 500`, `save_every: 250` and `sample_every: 250`; both keep `skip_first_sample: true` and `num_workers: 0`, and `max_step_saves_to_keep: 8` and every other value, `low_vram: false` included, are the trained config's. Both files are verified against their pinned sha256s (`PINNED_RUNG_YAML_SHA` and `PINNED_RUNG500_YAML_SHA`) before any `colab` call, and the selected file is uploaded to `/content/rung-qwen-image.yaml`. Its model is the local snapshot path, not the repo id, so ai-toolkit loads the pinned revision and not a Comfy-Org substitute. `run.py` runs with `HF_HUB_OFFLINE=1`. The dataset is 12 Salt Road plates (cc-by-4.0) with their captions; every plate is 1344x768, so ai-toolkit (which copies a dataset once per resolution and buckets each copy by area, `min(w*h, res^2)`) puts each in the 512, 768 and 1024 sets; with batch size 1 a 20-step run misses the 1024 set with probability (2/3)^20, about 0.03%.

**Copy-off** — while `run.py` runs, `lane3_rung.py copy-off` copies each checkpoint and sample whose size has held still into `lane3_out/rung_outputs/` and appends a line (path, bytes, sha256, and for a `.safetensors` whether it is `partial`: a header that does not parse or a size that does not match its data offsets) to `rung_outputs/manifest.jsonl`; a file that vanishes or cannot be read is logged `COPY_OFF_SKIPPED` and retried, never fatal (`lane3_rung.py:583-617`), and a final sweep runs in its own process after training (`launch_lane3_stub.sh:416`). A run with no complete checkpoint is `TRAIN_CHECKPOINT_MISSING` (`lane3_rung.py checkpoint`), with no sample image `TRAIN_SAMPLE_MISSING` (`:437`). The remote script bundles `lane3_out` on every exit it sees (an EXIT trap). A rig-side kill (wall, cap, stall, dead harness) stops only the local exec; the VM cell keeps running and holds the session's one kernel, so a new exec would only queue behind it (`docs/colab-cli-contract.md`, section 1). The kit's failure path (`colab_salvage_bundle_after_failure` in `colab_window.sh`, called by `lane3_download_bundle_after_failure`) therefore runs `colab restart-kernel` under `timeout -k 10 180` (190 s), then `lane3_bundle_now.py` on the VM (`colab exec --timeout 300` wrapped in host `timeout -k 10 330`, 340 s; `lane3_rung.py bundle-now`, `:704-770`: it SIGKILLs the rung's processes, sweeps the training folder, writes the failure record, scrubs and tars), and then downloads the bundle under `timeout -k 10 300` (310 s), all under one total salvage deadline (`SALVAGE_DEADLINE_S=840` s; past it, remaining salvage steps are skipped with `SALVAGE_DEADLINE_EXCEEDED <step>` and cleanup goes straight to `colab stop`). `cleanup_on_exit` installs a shell trap function (`colab_on_cleanup_signal`) instead of `trap '' TERM INT` and runs every bounded command in a subshell with `trap - TERM INT`, so child processes inherit default `SIGTERM`/`SIGINT` dispositions (`SIG_DFL`) while a late signal to the launcher does not abort `colab stop`. `colab stop` runs under `timeout -k 10 60` (70 s) with 1 retry (140 s total), giving worst-case `cleanup_stop_attempted_by_s = 840` s and `cleanup_bound_s = 980` s on Lane 3 (`0` s and `140` s on Lane 1), recorded in `window.json`. When a 500-step window is stopped after step 250 (for example by `CAP_GUARD_TRIPPED` or `WALL_GUARD_TRIPPED`) while the step-500 save is still in flight, the downloaded bundle keeps the complete step-250 checkpoint (`rustline_style_v5_000000250.safetensors`, listed in `rung_outputs.checkpoints`) and all 6 step-250 samples (`rung_outputs.samples`), marks the half-written step-500 checkpoint `partial` in `manifest.jsonl` (`rung_outputs.partial_checkpoints`), and records the stopped run (`trained: false`, `refusal_code` set to the guard refusal) in `window.json`. The `colab` CLI cannot download during an exec, so this protects a run that fails or is stopped, not a VM that is lost: true mid-run copy-off would need a Drive mount, and it is left out. `--train` needs explicit `--wall-s` and `--cap` (`TRAIN_WALL_REQUIRED`, `TRAIN_CAP_REQUIRED`), and the wall minus the grace must cover the download limit + 900 s install + 1800 s training (`TRAIN_WALL_TOO_SHORT`; `:625-659`).
