## Local walk (before any paid window)

The fake CLI checks what the kits send to Colab; it does not run the remote script. A local walk does: it runs the lane 3 remote script end to end on a Linux box, with real uv, the real interpreter download, the real lock, the real local wheels and the real ai-toolkit pin. It costs nothing and found three defects that the fake suite had passed (window `sdlab-l3-stub-4`'s lock file, a missing `torchaudio`, and a training failure with no `REFUSED` line).

1. **Emit the script.** `bash scripts/colab/launch_lane3_stub.sh --emit-remote-script <dir>/remote_lane3_stub.sh` writes the script through the same function the live path uploads with (`scripts/colab/launch_lane3_stub.sh:41`), so the file is byte for byte what a window would run, and writes `<dir>/remote_lane3_stub.sh.env` with the `KEY=VALUE` lines the kit passes to `colab exec --env` (`:444-454`). It exits before the pre-flight and makes no `colab` call. With any window option (`--out-dir`, `--session`, `--card`, `--wheel-dir`, `--cap`, `--wall-s`, `--grace-s`, `--margin`) it is refused `EMIT_REMOTE_SCRIPT_EXCLUSIVE` (`:488-504`; `tests/colab/test_lane3_local_wheels_lock.py`).
2. **Stage `/content` as the uploads leave it**, flat: `lane3.lock`, `lane3-local-wheels.json`, both wheels, `launch_guards.py`, `classify_install_log.py` and the emitted script.
3. **Give it a real `/content`.** Without root, bind a directory onto `/content` with `bwrap` (`--bind <dir> /content`, the system directories read-only, `--dev /dev` so no GPU device node is visible, `/usr/lib/wsl` hidden on WSL). Put a `pip` first on `PATH` that installs into a directory also on `PATH`, as Colab's root `pip` installs into `/usr/local/bin` (a seeded venv of the box's `python3` does). Run it through the kit's own `remote_runner.py` with `SDLAB_REMOTE_SCRIPT=/content/remote_lane3_stub.sh` and the `.env` values, a fresh `HOME`, and `taskset` for a thread cap. Keep the run's logs on a persistent disk.

**What it proves:** every file the script generates parses (the lock, the uv bootstrap requirement, the job YAML), the pinned uv, interpreter build, lock and wheels install on a clean Linux x86_64 box from the real indexes, the ai-toolkit pin checks out, the import gate passes, and the script runs on to its training step with its refusals named.

**What it does not prove:** anything that depends on the VM itself. Colab's system Python (3.13.16 measured on 2026-10-25) and its preinstalled packages differ from the box's, `/content` there is root-owned on its own disk, and the RAM ceiling, network egress and CPU count are Colab's. The walk on 2026-11-06 ran on Ubuntu 26.04 (glibc 2.43) with a `python3` 3.14.4 stand-in for Colab's root pip.

**What the lane 3 CPU stub proves now (from the install-path change):** the pinned uv, the CPython 3.12.15 build `20261021`, the hash-locked `lane3.lock`, the two local wheels, the ai-toolkit pin and the import gate, on the VM, ending with `TRAIN_SKIPPED`, `train: skipped_cpu_stub` and a downloaded bundle of the install evidence. Its acceptance ends at the import gate.

**What it does not prove:** anything about training. It never builds the synthetic package or job, never runs `run.py` and writes no checkpoint, and `trained` stays `false`. Training is a separate GPU rung, designed later with a real model configuration; the remote script keeps its training step behind `LANE3_MODE=train` for that rung, which the CPU stub never passes.

**Why lane 3 training cannot run on a CPU VM (walk of 2026-11-06):** ai-toolkit at `beb94824` imports every built-in extension when it builds a job, and `extensions_built_in/diffusion_models/omnigen2/src/ops/triton/layer_norm.py:46` calls `torch.cuda.current_device()` at import time, so on any machine without an NVIDIA driver (a Colab CPU VM included) `run.py` fails with `RuntimeError: Found no NVIDIA driver on your system`. Past that (checked by faking the device query, outside the kit), the synthetic job had no `model:` block and ai-toolkit refused `name_or_path must be specified`. The train mode now takes the model only from `LANE3_MODEL_NAME_OR_PATH` and refuses `TRAIN_MODEL_REQUIRED` without it; which model the GPU rung trains is its own decision.
