**The machine shape (every GPU window)** — google-colab-cli 0.7.4 turns `colab new --high-mem` into the assign URL's `shape=hm` (`colab_cli/client.py:302-303`) through `resolve_assign_shape` (`:97-111`), which drops it only for L4, V5E1 and V6E1 (`HIGH_MEM_ONLY_ACCELERATORS`, `:90-95`). The kits used to send `--high-mem` with every GPU card (`colab_window.sh:729` at `1f5c6e0c`), so a G4 was opened as High-RAM, a shape no receipt had priced (the G4 we measured is G4 Standard, 8.90/h, receipt `windowC2-48-g4-s1a-20261028`). Now a GPU card needs `--shape standard|high-mem` in both kits, with no default (`SHAPE_REQUIRED`, `SHAPE_INVALID`), checked by the shared `colab_shape_gate_arm` before any `colab` call; `colab_open_session_locked` refuses `SHAPE_REQUIRED` for a GPU card that was not armed, and sends `--high-mem` only for `high-mem`. Right after the open (the cap clock already running, before the rate read and any upload) `colab_check_session_shape` reads `colab sessions` and requires the session's row to print `Shape: High-RAM` for `high-mem` or `Shape: Standard` for `standard`; anything else, a missing row or a row with no Shape included, is `SHAPE_MISMATCH`, and the EXIT trap stops the session. `window.json` records `shape_requested` and `shape_check` (`requested`, `expected`, `observed`, `match`). **L4, V5E1 and V6E1:** the CLI sends no shape for them because they exist in a single high-memory shape (the comment at `client.py:90-91`), so the kits refuse `--shape standard` for them before any `colab` call (`SHAPE_STANDARD_UNAVAILABLE`) and expect `Shape: High-RAM` for `--shape high-mem`. **The live rate and cleanup-reserved cap guard (GPU windows and CPU stubs)** — `colab usage` prints `Current balance: <x> compute units`, `Usage rate: <r>/hr` and `Active assignments: <n>` (the fake prints the same three lines, as Publisher receipts show them). The rate is the account's, and it can read `0.00/hr` right after a session opens (rung 1, 2026-11-06). The cap guard spends max(balance drop, rate x elapsed) (`launch_guards.py`) and reserves the worst-case cleanup spend inside the cap (`compute_cap_trip` in `launch_guards.py`, called by `colab_window.sh`): `cleanup_reserve = (cleanup_bound_s / 3600) * priced_rate` and `effective_trip = cap - margin - cleanup_reserve`, where `cleanup_bound_s` is measured from the trip (`310` s in-flight foreground bound + `SALVAGE_DEADLINE_S` + `140` s two-attempt `colab stop` on Lane 3, i.e. `1600` s reserving `4.666667` CCU at `10.5`/h for 2-part rung jobs and `1290` s for $N=1$; `450` s on Lane 1: `310` s in-flight + `140` s stop, reserving `1.3125` CCU at `10.5`/h), and `priced_rate` is `max(--max-rate, highest stable window rate)` on GPU windows (re-evaluated on every live cycle so a rising window rate increases `cleanup_reserve` and lowers `effective_trip`) or the labelled CPU rate (`0.26`/h) on CPU stubs. Before any `colab` call (`colab_cap_budget_gate` / `launch_guards.py --check-cap-budget`), if `effective_trip <= 0` or the runtime to the trip at `priced_rate` is below `--min-runtime-s`, the kit refuses `CAP_TOO_SMALL_FOR_CLEANUP` with the arithmetic in `why`. Calling `launch_guards.py --dry`, `launch_lane1_stub.sh --dry`, or `launch_lane3_stub.sh --dry` prints `cap`, `margin`, `cleanup_bound_s`, `priced_rate`, `reserve` (`cleanup_reserve`), `effective_trip`, runtime to the trip at `priced_rate` and at `--max-rate`, both spend bounds (`worst_case_cap_path = cap` and `worst_case_launcher_death_path = (death_time + cleanup_bound_s) / 3600 * priced_rate`, where `death_time` is at most the moment the cap would trip) and their max (`worst_case_total_spend = max(cap_path, launcher_death_path) = cap`), plus one `assumptions:` line naming the assumption each bound rests on, making no `colab` calls. On a GPU card `COLAB_LIVE_RATE_REQUIRED=1` stops the projection from ever using the configured CPU rate; right after open `colab_read_post_open_rate` polls up to 24 times, 5 s apart, and refuses `RATE_UNREAD` without a positive rate, or `RATE_ABOVE_MAX` when the window's rate (post-open minus pre-open) is above `--max-rate`, before any upload. `window.json` keeps the reading as `rate_check`, plus `cleanup_reserve_units`, `effective_trip_units`, and `cap_trip_formula` (`cap_guard.formula`).

**Residual risk: external `SIGKILL` to the launcher** — no user-space signal handler or `EXIT` trap can catch `SIGKILL` (`kill -9`). If an external `SIGKILL` kills both the launcher process (`MAIN_PID`) and its background wall watcher before `colab stop` runs, the remote Colab session (VM, GPU/CPU assignment, and any running kernel/training processes) stays active on Google Colab's servers and continues billing compute units until server-side assignment expiry or manual stop. (If `SIGKILL` kills only `MAIN_PID` while the wall watcher survives: before the wall trip, the watcher's ~1 s `kill -0` poll detects that `MAIN_PID` is gone, kills tracked child processes, and runs bounded `colab stop -s <session>` itself with `watcher_wait: "launcher_gone_pre_trip"` and `stop_path: "watcher"`, starting the stop within about `1` s plus the in-flight kill grace of the launcher's death and completing within `stop_bound_s` after that; at or after the wall trip, it detects that `MAIN_PID` is gone immediately, kills tracked child processes, and runs bounded `colab stop -s <session>` itself with `watcher_wait: "escalated_launcher_gone"`, finishing within `cleanup_bound_s` of the trip.) Any stranded session is surfaced automatically on the next window's open via `colab sessions` (`sessions_after_open.txt`) and `colab usage`'s `Active assignments` count, or can be found and stopped manually from the rig with `colab sessions` and `colab stop -s <session>`.
